# Releasing

The extension ships as a zip per browser (Chrome, Edge and Firefox). Cutting a release builds and
checks all three packages, and publishes them as GitHub release assets. Store submission is a
separate, manual step: both stores tie a listing to a developer account and review every upload.

## Cutting a release

1. Bump the version in `manifest.jsonnet` and add a section to `docs/content/changelog.md`:

   ```bash
   sed -i "s/^local version = .*/local version = '0.6.0';/" manifest.jsonnet
   ```

   The changelog heading uses the short version (`# v0.6 - 2026-11-01`), because that is what the
   release workflow looks up when it builds the release notes.

2. Refresh the search index if cppreference has moved since the last release (`make index`); the
   monthly `refresh-index.yml` workflow opens a pull request when it has.

3. Commit, push, and check the build before tagging:

   ```bash
   git commit -am 'Release version 0.6.0' && git push
   gh workflow run release.yml            # builds and checks the packages, publishes nothing
   ```

4. Tag and push. `.github/workflows/release.yml` then builds `cpp-search-extension-0.6.0-chrome.zip`,
   `-edge.zip` and `-firefox.zip`, checks each package (manifest at the archive root, version equal
   to the tag, MV3 for Chrome/Edge and MV2 for Firefox, search index present) and creates the GitHub
   release with the changelog section as its notes:

   ```bash
   git tag v0.6.0 && git push origin v0.6.0
   ```

   A tag whose version does not match `manifest.jsonnet` fails the run before anything is built.

## What the packages contain

`extension/` is the whole package: `manifest.json` (generated by jsonnet from `manifest.jsonnet`),
`core/` (copied from the `core` submodule), the prebuilt indexes under `index/`, the search code,
the options page and `logo.png`. Nothing else is zipped, and no code is fetched at runtime, which
is what the stores' "no remote code" policy requires.

Store submission per browser:

| Browser | Package | Where it goes |
| --- | --- | --- |
| Chrome | `-chrome.zip` (MV3) | Chrome Web Store, uploaded by hand or with the Chrome Web Store API |
| Edge | `-edge.zip` (MV3, same manifest as Chrome) | Edge Add-ons, uploaded by hand or with the Edge Add-ons API |
| Firefox | `-firefox.zip` (MV2, `background.scripts`) | addons.mozilla.org, signed by `web-ext sign` or uploaded by hand |

Firefox only accepts signed builds for release installs, so the zip in the GitHub release is a
build artifact, not something users can install permanently.

## Store accounts and listings

Both stores need a developer account once, before the first upload:

- **Chrome Web Store** — one-time 5 USD registration, the account needs 2FA and identity
  verification, and a merchant/trader declaration for the EU. Then "New item" takes the zip.
- **Edge Add-ons** — free; register in the Microsoft Partner Center ("Edge" program) with any
  Microsoft account.
- **addons.mozilla.org** — free; an API key pair from the AMO developer hub enables
  `web-ext sign --api-key ... --api-secret ...`.

### The upstream listings cannot be reused

The extension is already on both stores, published by the upstream author, but they are stuck on
older builds and cannot be updated from this repository:

| Store | Listing | Published version | Users |
| --- | --- | --- | --- |
| Chrome Web Store | `ifpcmhciihicaljnhgobnhoehoabidhd` | 0.4.0 | ~3k |
| Edge Add-ons | `ffajabficigcddnckikojejmkammkmpe` | 0.4.0 | — |
| addons.mozilla.org | `c-c-search-extension` | 0.4.0 | 189 |

A listing belongs to the account that created it, so this fork has two options:

1. **Take over the existing listings** — the upstream author has to add this account to the
   publisher group (Chrome) or transfer the item (Edge, and AMO has an ownership transfer form).
   That keeps the users, reviews and the `cpp.extension.sh` links, and is the only way to ship the
   fix to the ~3k existing users. Worth asking for, given the fork exists to fix the stale index.
2. **Publish new listings** — pick a distinguishable name (e.g. "C/C++ Search Extension (updated
   index)"), and accept that users have to find it themselves; the upstream listing keeps serving
   0.4.0.

Two builds of the same extension cannot share an item id, so this decision comes before the first
upload, not after.

## Listing material

Prepared once per listing and reused for every upload:

- Store icon 128x128 (the repository's `extension/logo.png`), plus screenshots: 1280x800 or
  640x400, one to five of them. The omnibox dropdown with a search result is the useful shot.
  All icon sizes in the manifest point at that one file, so the 16px toolbar icon is a downscaled
  128px image; adding real 16/48 px files would sharpen it.
- Short description (132 characters in Chrome, 250 in Edge) and the full description from the
  README; category "Developer Tools"; the language.
- Homepage and support URLs. `cpp.extension.sh` belongs to the upstream author, so a fork points
  at its own repository instead.
- Privacy: the extension collects nothing — settings and the local search history stay in
  `chrome.storage.local`, and the only network request is the page the user picks (a cppreference
  URL or the user's own offline docs). The dashboards still ask for the data-usage declaration
  ("does not collect user data"), and Chrome asks for a privacy policy URL once an item handles
  data. Say in the description that this is an unofficial client for cppreference.com, since the
  name must not look endorsed by it.
- Permission justifications: `storage` (settings and history) and `unlimitedStorage` (the offline
  docs index is read from the user's own disk). `unlimitedStorage` is the one permission that
  occasionally slows a review down; it cannot be dropped because offline mode resolves paths under
  a user-chosen directory.

Review takes a few days on Chrome (longer for permission-heavy items) and up to about a week on
Edge. Uploads are only visible to users after the version is published in the dashboard, and every
store requires an increasing version number, so reuse a version only while it is still a draft.

## Automating the store upload

Both stores have an API for upload and publish, which is how a release can push to the stores from
CI instead of clicking through dashboards. Neither is enabled in this repository yet: each needs
credentials that only the account owner can create.

Chrome Web Store API (v2), with `chromewebstore` scope and a refresh token:

```bash
TOKEN=$(curl -s -X POST https://oauth2.googleapis.com/token \
  -d client_id="$CWS_CLIENT_ID" -d client_secret="$CWS_CLIENT_SECRET" \
  -d refresh_token="$CWS_REFRESH_TOKEN" -d grant_type=refresh_token | jq -r .access_token)

# upload the zip, then send the item to review
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/zip" \
  --data-binary @cpp-search-extension-0.6.0-chrome.zip \
  "https://chromewebstore.googleapis.com/upload/v2/publishers/$CWS_PUBLISHER_ID/items/$CWS_ITEM_ID:upload"
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  "https://chromewebstore.googleapis.com/v2/publishers/$CWS_PUBLISHER_ID/items/$CWS_ITEM_ID:publish"
```

Creating `CWS_CLIENT_ID`/`CWS_CLIENT_SECRET` means a Google Cloud project with an OAuth consent
screen, then `CWS_REFRESH_TOKEN` comes from one interactive consent; the token does not expire.

Edge Add-ons API, with an API key created in Partner Center:

```bash
curl -s -X POST \
  -H "Authorization: ApiKey $EDGE_API_KEY" -H "Content-Type: application/zip" \
  --data-binary @cpp-search-extension-0.6.0-edge.zip \
  "https://api.addons.microsoftedge.microsoft.com/v1/products/$EDGE_PRODUCT_ID/submissions/draft/package"
# then poll the operation, and publish the submission when it succeeded
```

If these are added to `release.yml`, keep them behind a `workflow_dispatch` input or a GitHub
Environment with required reviewers: publishing to a store is what users install, and a bad upload
can only be followed by another upload with a higher version number. The release job runs with
`contents: write`; the store tokens belong in repository secrets, never in the workflow file.

## Version history notes

- 0.5.0 rebuilt the search index (2025-02 cppreference snapshot, 19960 names instead of 13018) and
  ranks results by match quality; a store upload of it is what fixes `std::print` for existing
  users.
- Offline mode resolves `file://<offline path>/<cpp/symbol>`, so the offline docs a user points at
  must match the index version; the options page path (`file:///home/me/cppreference/en/`) is worth
  a note in the release notes whenever the index is regenerated.
